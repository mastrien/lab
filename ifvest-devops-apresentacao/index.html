02 · Padronização de Ambientes

Contêineres com Docker Compose (Dev, CI e Prod)

Desenvolvimento docker-compose.yml
  • • Sobe db, api (:8000) e web (:3000) com um comando.
  • • Bind mount de src/ e static/ na API para agilidade local.
  • • healthcheck + depends_on: service_healthy.
  • • Dados do PostgreSQL preservados no volume pgdata.
Simulação de CI docker-compose.ci.yml
  • • Serviço pg-ci em tmpfs (porta 55432) para velocidade.
  • • Perfis Linux (--profile linux): backend-ci (Python 3.12) e frontend-ci (Node 20).
  • • Permite reproduzir localmente as mesmas checagens do GitHub Actions.
Produção (VPS) docker-compose.prod.yml
  • • Nome fixo name: ifvest-deploy para proteger o nome dos volumes.
  • • ENVIRONMENT=production, MOCK_AUTH=false e AUTO_CREATE_TABLES=false.
  • • Volumes: pgdata, api_static e caddy_data.
  • • Frontend compilado com VITE_API_URL="" (mesma origem, sem CORS).
Ponto de atenção: Embora o uso de contêineres aproxime desenvolvimento e produção, ele não elimina diferenças de configuração entre os ambientes (autenticação mock, criação automática de tabelas, variáveis de CORS, certificados TLS e volumes).

04 · Primeira Barreira de Qualidade

Hook Local pre-push

Comportamento Inteligente

  • 1. Analisa o diff enviado pelo git push e identifica alterações por pasta (ifvest-backend/ e/ou ifvest-frontend/).
  • 2. Alerta caso a branch local esteja atrás da origin/main (pois o CI testa a junção com a main).
  • 3. Se houver Docker disponível, sobe um PostgreSQL 16 efêmero (tmpfs) para validar migrations localmente.

Portões Executados Antes do Envio

Backend (Python)
ruff check . · ruff format --check . · pytest --cov-branch --cov-fail-under=90
Frontend (React / TS)
npm run lint · npm run test:ci (≥90%) · npm run build (tsc + vite)
Instalação automatizada: O script npm run prepare configura os hooks do repositório (.githooks/), alinhando a validação local aos mesmos critérios que reprovam um PR no CI.
05 · Integração Contínua

Workflows no GitHub Actions

CI — Backend

ci-backend.yml
  • • quality: Ruff (lint + format + McCabe ≤ 9), Pytest com cobertura de branches ≥ 90% e check de inicialização da API.
  • • postgres: Sobe postgres:16-alpine para testar migrations e compatibilidade SQL real.
  • • docker: Valida o build da imagem Docker do backend.

CI — Frontend

ci-frontend.yml
  • • quality: ESLint (--max-warnings 0 + sonarjs), Vitest com cobertura ≥ 90% e build (tsc --noEmit && vite build).
  • • docker: Valida o build da imagem Nginx/produção do frontend.
  • • Publica artefatos de cobertura para auditoria.

E2E — Playwright

e2e.yml
  • • Acionado quando backend ou frontend mudam.
  • • Sobe PostgreSQL 16 real + backend + frontend Vite e executa 9 suítes no Chromium.
  • • Retém relatórios do Playwright por 14 dias em caso de falha.

Testes de Mutação

mutation.yml
  • • Execução semanal (segundas, 06:00 UTC) e sob demanda.
  • • Backend (mutmut): avalia 12 módulos críticos (permissões, segurança, redação, importação).
  • • Frontend (Stryker): thresholds break: 60 / low: 70 / high: 85.
06 · Evolução de Banco & Publicação

Migrations com Alembic e Deploy em Produção

Validação Automática de Schema (test_migrations.py)

  • • Cadeia única: exige exatamente 1 head a partir da base 1ecaa35837ac (13 revisões atuais).
  • • Round-trip completo: executa upgrade head → compara schema com modelos SQLAlchemy (compare_metadata) → downgrade base → upgrade head.
  • • Trava de segurança: aborta se o nome do banco não contiver test ou migrations.
  • Limitação: valida estrutura em banco de teste, mas não substitui cuidados com dados reais de produção.

Fluxo de Publicação Manual (cd.yml)

  1. Disparo manual via workflow_dispatch (alvo: all, web ou api).
  2. Sincronização de código para a VPS via rsync sobre SSH.
  3. Build das imagens e subida do db aguardando status healthy.
  4. Execução de alembic upgrade head antes da API: se falhar, o deploy interrompe e a versão anterior permanece ativa.
  5. Subida dos serviços (--remove-orphans) e verificação HTTP 200 em /, /health e /api/v1/features.
07 · Engenharia Assistida por IA

Convenções em Camadas: Arquivos AGENTS.md

Estrutura em 3 Níveis
  • • AGENTS.md (raiz): regras arquiteturais, migrations, schemas e política de testes.
  • • ifvest-backend/AGENTS.md: convenções Python/FastAPI.
  • • ifvest-frontend/AGENTS.md: convenções React/TypeScript.
Estilo & Arquitetura
  • • Funções curtas (4 a 20 linhas) e arquivos < 500 linhas.
  • • Máximo 2 níveis de indentação (early returns) e sem duplicação (DRY).
  • • Tipagem estrita (sem any ou Dict genérico).
  • • Injeção de dependências e preservação de comentários de intenção.
Anti "Coverage Game"
  • • Proibição de asserções vazias (toBeTruthy, is not None).
  • • Exigência de validar valores exatos e fluxos de erro (401/403/404/422).
  • • Fakes/mocks nomeados em vez de stubs frágeis.
  • • Bugs corrigidos exigem teste de regressão.
Limite prático: A leitura dos arquivos AGENTS.md depende do suporte da ferramenta de IA utilizada, e nem todas as diretrizes (como qualidade semântica de asserções ou clareza de nomes) são verificáveis automaticamente — exigindo revisão humana nos PRs.
08 · Gestão Colaborativa

Fluxo de Contribuição e Revisão por Pares

As 5 Regras de Ouro (CONTRIBUTING.md)

  1. Nunca enviar direto para a main (regra cultural apoiada pelo time no plano gratuito).
  2. Uma branch por tarefa: PRs menores revisam mais rápido e evitam conflitos.
  3. Todo código novo vem com teste (meta de 90% de cobertura).
  4. Explicar cada linha do PR — inclusive o código gerado por IA.
  5. Pedir ajuda cedo com contexto estruturado (objetivo, comando, erro e tentativas).

Ciclo da Tarefa & Onboarding

  • • Trilha de guia (docs/guia/): passo a passo de ambiente, Git do zero, escrita de testes e primeiro PR.
  • • Fluxo padrão: main atualizada → branch tipo/tarefa → código + testes → pre-push → PR → CI verde + revisão → Squash and merge.
  • • Template de PR (.github/pull_request_template.md): mapeia riscos de migration, permissões, contrato da API e exige confirmação de revisão linha a linha da IA.
09 · Conclusão

Síntese: O que as Práticas Entregam e Seus Limites

Camadas de Proteção Conquistadas

  • ✓ Infraestrutura reproduzível com persistência e rede isolada via Caddy + HTTPS.
  • ✓ Detecção precoce de falhas: hook pre-push + CI (lint, 90% cobertura, E2E e mutação semanal).
  • ✓ Evolução controlada de schema (Alembic validado em Postgres real antes do deploy).
  • ✓ Documentação viva (AGENTS.md + CONTRIBUTING.md) alinhando alunos e IA.

Limites Reconhecidos pela Equipe

  • • Contêineres aproximam dev e produção, mas não eliminam diferenças de configuração.
  • • Verificações no CI reduzem regressões, mas não garantem ausência total de falhas.
  • • Testes de migrations em banco descartável não substituem testes com dados reais de produção.
  • • Diretrizes em AGENTS.md dependem de adesão da ferramenta de IA e revisão humana.
